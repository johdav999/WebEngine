# Simulator quality and condition

Include engine/simulator/quality.hpp and link WebEngine::Simulator. These optional standard-C++20 value mechanisms own no clock, renderer, platform, inventory, ledger, task graph or asset. The application owns product/lot identities, freshness effects, quality composition, equipment thresholds, use-source IDs and maintenance policy.

Freshness{madeAt, lifetime, baseQuality} uses integer milliseconds and a quality scale of 0-1000. valid() checks nonnegative creation time, positive shelf life up to one year, quality bounds and deadline overflow. sample(now) rejects times before creation; otherwise it returns score, remaining milliseconds and expired. At the exact deadline score and remaining become zero and expired becomes true. Before expiry score is floor(baseQuality * remaining / lifetime). Bounded shelf life makes the integer product safe and deterministic across native/Wasm hosts. The helper retains no current time and does not mutate stock.

Condition owns ConditionState{integrity=1000, cleanliness=1000, lastUse=0, uses=0}. use(source, wear, dirt) checks positive increasing stable source IDs, 0-1000 wear/dirt and counter bounds, then applies saturating subtraction once. Gaps are valid for production jobs cancelled before start. Repeated/old IDs return AlreadyTerminal without effects. clean() restores cleanliness only; repair() restores integrity only. They preserve use counters. snapshot/restore are typed; invalid bounds or inconsistent use watermarks leave the value unchanged. Host persistence ties a condition to the matching equipment and source sequence.

Runtime::remove(inventory, amounts) is an atomic positive unique-resource bundle sink for disposal and other host-owned consumption. Every amount must be available after all stock reservations. It never takes held production inputs or claimed outputs, and it preserves incoming capacity holds. Invalid IDs, quantities, stock or event pressure publish no part of the removal. One StockRemoved event identifies the inventory at Runtime time; no reservation record/ID is allocated. The source engine uses its existing staged state publication.

CafeGame samples base product quality from the lower pre-use machine metric, applies 100 wear and 150 dirt per started production job, gates new brewing below 300 in either metric and assigns a 45-second espresso shelf life from actual job completion. Expiry abandons the order through core rules, then removes the released cup without a receipt. Cancelled/abandoned output is counted as waste and discarded. Coffee prices remain fixed; ingredient-lot modelling, temperature, random failures and satisfaction pricing are future integrations.

The game uses existing TaskBoard priority-30 barista tasks for two-second free machine cleaning and four-second repairs prepaid at 5.00. They navigate to the existing machine point, preserve remaining work through breaks and restore the matching metric once on completion. Service is gated during maintenance. Cancellation before completion refunds the pending repair once; completed repairs cannot be refunded. Ledger preparation precedes task creation/cancellation, and exclusive owner-thread publication preserves cost/effect consistency. Wages use the existing on-shift policy.

Core snapshots stay schema 1. CafeGame envelope 6 persists condition/source watermark, base quality, cup freshness origin, waste, maintenance task/type/cost, typed workflows, cash and core state together. Candidate load validates task identity/role/duration, no conflicting service, job completion time, freshness, reservations and ledger costs. Epochs/tokens are rebased through the existing core/task loaders. Legacy formats 1-5 start with a fully maintained machine, bind the current started job watermark and retain a ready cup's real completion time. They create no retroactive wear or maintenance costs; already-old cups expire on a subsequent simulation boundary.

Generic contracts cover freshness boundaries/overflow, source idempotency, independent maintenance effects, typed state rejection, mixed-bundle removal and reserved/outbox atomicity. Cafe tests cover expiry without payment, disposal conservation, busy/broken/dirty gates, stale arrival protection, interrupted maintenance, exact refunds, invalid saves and migration. Validation on 2026-10-25: WebEngine's WebAssembly CTest suite passed 4/4, including the generic quality and atomic removal contracts. The standalone Edge 156 runner reported 870 checks and no errors. CafeGame's WebAssembly simulation suite passed 1/1, and complete rendered scenarios passed under forced WebGL 2 and automatic software-renderer fallback, covering freshness expiry without payment, waste, cleaning, repairs/refunds and interrupted maintenance persistence. All 12 bundled-source hashes and canonical/bundled quality test copies matched; all three actual engine-skill copies document the additions. The renderer pin and core snapshot schema remain unchanged.

Native Windows/Linux execution, full Linux cloud validation, hardware WebGPU and physical mobile performance were not tested in this run. No native compiler was found in the checked Windows toolchain locations. Software-rendered browser checks establish functional behavior only. No paid generation, commit or push was performed.
