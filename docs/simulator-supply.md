# Simulator supply and inventory transfer

Include engine/simulator/supply.hpp; link WebEngine::Simulator. Standard C++20 only, shared by browser and native consumers. Supply is optional above the existing inventory/reservation kernel; it creates no renderer, navigation, task board, clock, IO or economy dependency.

Runtime::transfer(source, destination, amounts) checks an entire positive unique-resource bundle, available unreserved source stock, and destination free capacity after incoming holds. Same-inventory transfers are rejected. One staged publication subtracts and adds every amount together. Two adjacent StockTransferred events identify source then destination at the same simulation time. Insufficient event room, capacity, stock or invalid IDs leaves all stock and events unchanged; no ID or reservation is allocated. Existing reserved inputs remain untouched.

SupplyBoard(runtime, limit=64) borrows a Runtime which must outlive it and remain on the same owner thread. Use one board for a Runtime's supplier orders; SupplyId epochs belong to that Runtime. The board is noncopyable/nonmovable because it owns reservations. Destroying a board does not cancel orders; cancel/retire them explicitly or persist and rebind them. Borrowed order views expire on mutation. Limits are 1-4096 retained orders, 1-64 bundle entries, and 64-character namespaced supplier keys. place(supplier, destination, amounts, positiveLeadTime) returns a SupplyId, reserves output capacity immediately, and records an absolute Runtime-time deadline. No goods enter stock before delivery. Allocation/preflight failure publishes no helper record or capacity hold. The host must not independently finish/forget reservations owned by the board.

poll() explicitly commits due pending orders in (deadline, ID) order. Each delivery is atomic across the reservation and helper record and happens once. The host supplies time by Runtime::advance, then polls at its chosen simulation boundaries. Late polling delivers at the current Runtime time, with no wall-clock or offline catch-up assumption. For an error, the result counts the successfully committed prefix; the failing order stays pending. Drain event pressure and retry. This is per-order atomicity, not an all-orders transaction.

cancel(id) releases a pending hold; repeated delivery/cancellation is rejected. forget(id) retires terminal order and reservation records together. Pending orders cannot be forgotten; IDs are monotonic and never reused. Bounded histories require explicit retirement.

reorder(ReorderPolicy{supplier, destination, resource, threshold, target, leadTime}) orders the deficit to target only when inventory position (total stock plus all reserved incoming capacity) is at or below threshold. Target must exceed a nonnegative threshold and fit storage. Incoming orders count before delivery, so repeated calls do not duplicate a deficit. Reserved production inputs still belong to inventory position. A successful result with a zero SupplyId means no order was required. Choosing suppliers, enabling the policy, transferring stock and charging money remain host policy.

SupplySnapshot stores sequence and typed order records. Save it beside core bytes. Restore the core first, rebase every SupplyId, InventoryId and ReservationId to the restored epoch, create a fresh board, then restore the typed snapshot. It checks bounded records, strictly increasing IDs below sequence, supplier keys, unique reservation ownership, exact canonical amounts, destination, output-capacity kind and state/deadline consistency. Invalid restore does not replace the board. Restoring a Runtime invalidates existing boards and old handles; rebinding is explicit. Events and runtime epochs remain transient. Core wire format stays schema 1.

CafeGame uses a 24-bean storeroom, twelve-bean deliveries in eight simulation seconds, four-bean transfers, optional threshold-four/target-twelve ordering, and auto-transfer at machine total <=1. Its browser starts with four beans. Supplier samples are free; pricing/ledger, supplier stock/catalogues, trucks, spoilage and staff hauling are not implemented by this stage. Its schema-4 envelope validates pending supply holds together with spatial/workflow/wallet/core state, and migrates formats 1-3.

Tests cover mixed-resource conservation, input/capacity holds, invalid bundles, output pressure, order record bounds, exact deadlines, idempotency, cancellation/retirement, reorder suppression, stale epochs, rebased typed restore, malformed saves and interrupted Cafe delivery restoration. Platform execution evidence is recorded after validation below; shared portable source does not establish native or GPU acceptance by itself.
